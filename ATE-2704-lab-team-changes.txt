4. SHUTDOWN PROCESS FOR THIS LAB
--------------------------------

  On the Manager, as holuser:

      python3 /vpodrepo/2027-labs/2704/Shutdown/Shutdown.py --dry-run   (preview)
      python3 /vpodrepo/2027-labs/2704/Shutdown/Shutdown.py             (real run)

  Do NOT run the core "python3 Shutdown/Shutdown.py" in ~/hol for this lab:
  it skips the Aria Automation service shutdown (see 7.2).
  Make sure /tmp/config.ini is this lab's file (vPod_SKU = ATE-2704).
  Expect about 90 minutes in total, most of it the vSAN elevator.

  Step / phase     Action                                        VMs / hosts
  ---------------  --------------------------------------------  --------------------------
  Pre (wrapper)    deploy.sh --shutdown over SSH                 auto-01b (services)
                   (usually 10-20 min, max 45)
  0 / 0b           Pre-checks; Docker host (none, skipped)       -
  1                Fleet API (not on 5.2.1, skipped)             -
  1b               Guest OS shutdown through vCenter             auto-01b
  2                Connect to the three vCenters                 -
  3 / 3b / 3c      Stop WCP, pause Supervisor clusters,          vc-wld01-b Supervisor
                   power off control plane VMs
  4                Workload VMs (+ discovered Supervisor VMs)    user-vm-a, user-vm-b
  5 / 6 / 7        Workload Edges, NSX Manager, vCenter          edge-wld01-01b/02b,
                                                                 nsx-wld01-01b, vc-wld01-b
  11 / 12          Identity broker, Suite Lifecycle              vidm-01b, opslcm-b
  14 / 15 / 16     Management Edges, NSX Manager, SDDC Manager   edge-mgmt-01b/02b,
                                                                 nsx-mgmt-01b, sddcmanager-b
  17               Management vCenters                           vc-mgmt-b, vc-mgmt-a
  17b / 17c        Direct ESXi sessions; re-check post-Edge VMs  opslcm-b, vidm-01b, auto-01b
                   (already off by then)
  18 / 19 / 19c    Host advanced settings, vSAN elevator,        all 12 hosts
                   straggler audit
  20 / 21 / 22     Host shutdown, cleanup, wait for power off    esx-01a..04a, esx-01b..08b

  Then, in this order:
    1. Router: log in as root, run /root/shutdown.sh (before the Manager -
       the router has an NFS mount from the Manager).
    2. Shut down the Manager (before the console - NFS mount from the console).
    3. Shut down the console.

  Verified 2026-11-04 with a full --dry-run of the wrapper: the Aria step
  found deploy.sh on auto-01b (Aria Automation 8.18.1 build 24282366), and

5. STARTUP PROCESS FOR THIS LAB
-------------------------------

  No core change. At boot labstartup.sh:
    1. Reads vPod_SKU = ATE-2704 / labtype = ATE from the console's vPod.txt.
    2. Clones https://github.com/Broadcom/ATE-2704.git into
       /vpodrepo/2027-labs/2704 - branch "dev" on a Holodeck dev pod
       (guestinfo.ovfEnv empty or containing "dev"), "main" in production.
    3. Copies its config.ini to /tmp/config.ini.
    4. Runs the ATE startup sequence. choose_file() picks up
       Startup/VCFfinal.py from the vPod repo; all other modules are core.

  Module          What it does for ATE-2704
  --------------  -----------------------------------------------------------
  prelim          Core preliminary tasks (desktop, DNS checks, firewall/proxy)
  ESXi            Checks all 12 hosts and their ports
  VCF             Exits maintenance mode; waits for vsan-mgmt-01a,
                  vsan-mgmt-01b, vsan-wld01-01b; starts nsx-mgmt-01b and
                  nsx-wld01-01b; the four Edges; then opslcm-b, vidm-01b,
                  auto-01b (x-region network needs the Edges); then
                  vc-mgmt-a, vc-mgmt-b, vc-wld01-b
  vSphere         Connects to the three vCenters, checks datastores, starts
                  sddcmanager-b, user-vm-a, user-vm-b
  pings           21 IP addresses
  services        15 TCP ports
  urls            10 URLs (Aria Automation is checked later by VCFfinal)
  (services: 14 TCP ports - auto-01b:443 is checked by VCFfinal, see 6b)
  VCFfinal        LAB OVERRIDE - Supervisor wait, auto-01b power-on,
                  Aria Automation URL wait (see section 2)
  final           Core final tasks (ready status)

  Verified 2026-11-04 on the dev Manager:
    - "--standalone --dry-run" of ESXi, VCF, vSphere, pings, services, urls
      and the VCFfinal override: all exit 0 with the expected VM/host lists.
    - Live checks against the running lab: 21/21 pings, 15/15 TCP ports,

    - prelim and final were not dry-run (desktop/firewall/ready status only).

6b. FIRST REAL SHUTDOWN / STARTUP TEST (2026-11-04) - FINDINGS AND FIXES
------------------------------------------------------------------------

  SHUTDOWN (wrapper, 12:10-12:46, 33 min): deploy.sh --shutdown stopped the
  Aria Automation services in 181 s; every phase completed; vSAN is ESA so the
  elevator was skipped; the final audit shut down 6 vCLS VMs and demo-002 (an
  Aria test deployment); all 12 hosts were off after 106 s.

  STARTUP failed in "services", was fixed, and completed (Ready at 14:59).
  Two causes:

  1. The holorouter lost the Site B policy routing rules at boot.
     /etc/rc.d/init.d/startup_script.sh adds rules 901-904
     (10.2.12-15.0/24 -> table 20). Three seconds later systemd-networkd starts
     and deletes every routing rule it did not create itself (its default,
     ManageForeignRoutingPolicyRules=yes). The x-region network (Suite
     Lifecycle, vIDM, Aria Automation) and seg-01b became unreachable, so the
     pings and the required services check failed. Rules 901/902 date from
     2026-10-29 and 903/904 from 2026-11-03; both had been added at runtime and
     this was the router's first reboot since.
     FIX: /etc/systemd/networkd.conf.d/10-keep-lab-routing-rules.conf
          [Network]
          ManageForeignRoutingPolicyRules=no
     (directory mode 755 so networkd can read it). This is a HOLOROUTER IMAGE
     CHANGE - please carry it into the router template.
     Pre-existing, unrelated: startup_script.service always ends "failed"
     because of six generated lines "ip link add ... eth1.Routed type vlan id
     Routed" (no VLAN ID or address). Harmless, but it hides real failures.

  2. Aria Automation services do not start by themselves after
     "deploy.sh --shutdown". That command removes the services; Broadcom's
     start procedure is to run /opt/scripts/deploy.sh after power-on (20-40
     min). After a plain guest shutdown they restart on their own, so this
     follows from the shutdown wrapper.
     FIX: Startup/VCFfinal.py v1.2, new Task 2b: wait for the appliance's
     Kubernetes node, then start deploy.sh in the background if no pods exist
     in the prelude namespace (skipped if pods exist or deploy.sh is already
     running). config.ini v2.3: new [VCFFINAL] vra_start_hosts and
     vra_node_wait_minutes; auto-01b:443 removed from TCPServices (the port is
     closed until deploy.sh finishes; [VCFFINAL] vraurls checks it instead);
     vraurl_wait_minutes 35 -> 60, and [VPOD] maxminutes 60 -> 90 (the
     overall limit is checked in every module wait, so it also caps the
     Aria wait).
     In this test deploy.sh had been started by hand, so Task 2b took its
     "already running" branch; the "start it" branch runs on the next full boot.

7. REQUESTS FOR THE CORE TEAM
-----------------------------

  7.1 Shutdown overrides are never used.
      Shutdown.py loads VCFshutdown.py from its own folder and nothing calls
      choose_file('Shutdown', ...), so a Shutdown/ folder in a vPod repo or
      labtype folder is ignored. That is why this lab needs a wrapper run by
      its full path. A small hook in Shutdown.py, for example "run
      <vpodrepo>/Shutdown/pre-shutdown.py if it exists", would let labs drop
      the wrapper.

  7.2 Phase 1b assumes VCF 9.x Automation.
      The Kubernetes clean-up uses fixed addresses 10.1.1.69-74 and
      vmware-system-user, then a guest shutdown with a 300 s limit before a
      hard power off. For Aria Automation 8.x ([VCFFINAL] vravms) it should
      run /opt/scripts/deploy.sh --shutdown as root first and allow a longer
      wait.

  7.3 Phase 1 only probes Region A (ops-a, opslcm-a).
      A config key for the Fleet / Suite Lifecycle FQDN would let Site B and
      5.x labs use it.

  7.4 Please keep these working as they do now:
      [VCFFINAL] tanzucontrol and vravms, and the [SHUTDOWN] keys in section 3.

  7.5 labstartup.py --dry-run is accepted but ignored.
      It should either be honoured or removed, so nobody starts a lab by
      accident while testing.

  7.6 vSphere.py cannot enable vCenter SSH on vCenter 8.0 U3.
      It sends PUT /api/appliance/access/ssh with the body "true"
      (json=True). vCenter 8.0 U3 answers HTTP 400; it expects
      {"enabled": true}. On 2026-11-04 vc-wld01-b came up with SSH off, the
      startup could not fix it ("Failed to enable SSH (HTTP 400)"), and the
      next shutdown could not stop WCP or pause the Supervisor (Phase 3/3b
      "SSH port not reachable"); vCenter then restarted the control plane VMs
      and Phase 19c had to power them off. SSH was then enabled with
      {"enabled": true} (HTTP 204). The bash-shell call (access/shell) also
      returns HTTP 500 on all three vCenters; harmless here because root's
      shell is already bash.
